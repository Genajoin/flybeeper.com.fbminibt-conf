## P1 — навигация: нет постоянного меню

**Симптом.** Разделы (`/`, `/cockpit`, `/settings/*`, `/devices/<sku>`,
`/update/*`, `/terminal`, `/share`) живут каждый своей жизнью. Переход между
ними возможен только через ситуативные ссылки: `PageHeader` даёт крошку
«← DASHBOARD», аккордеон в `SettingsPanel` переключает только группы настроек,
а со страницы прибора (`/devices/<sku>`) в настройки прямого пути нет.

**Что сделать**

- [ ] Один постоянный навигационный элемент, видимый на КАЖДОЙ странице:
      Прибор · Настройки · Прошивка · Мануал · Терминал. На узких экранах —
      нижняя панель (телефон в руках у пилота — это основной сценарий).
- [ ] Активный раздел подсвечен; переход между разделами не теряет состояние
      подключения.
- [ ] Убрать одноразовые «крошки» там, где их заменяет постоянное меню.

## P1 — сценарий «отсканировал QR»

**Симптом.** QR ведёт на страницу устройства (мануал + обновление прошивки).
Для нового владельца это тупик: главное действие (подключиться и настроить)
на этой странице не предлагается.

**Что сделать**

- [ ] На `/devices/<sku>` вверху — явный первичный CTA «Подключить прибор»
      → после подключения сразу «Настройки».
- [ ] Три равноправных действия на странице прибора: **Настроить** ·
      **Обновить прошивку** · **Мануал**. Сейчас визуально доминирует прошивка,
      хотя это самое редкое действие и самое рискованное для новичка.
- [ ] Первый вход (нет сохранённых приборов) → короткий онбординг:
      подключить → что настроить в первую очередь (громкость, пороги) →
      где мануал.

## P2 — честность состояния настроек

- [x] Диалог расхождений показывает человеческие названия настроек, а не UUID.
- [ ] Если часть характеристик не прочиталась с прибора
      (`bluetoothStore.incompleteChars` не пуст) — сказать об этом в интерфейсе
      и предложить переподключиться. Сейчас поле просто выглядит обычным.
- [ ] `VIRTUAL_CPF_FORMAT` (офлайн-фоллбэк форматов) расходится с тем, что
      реально отдаёт прошивка:
      | UUID | в приложении | на приборе (FBminiBT) |
      | --- | --- | --- |
      | `9a560750…` power off timeout | uint32, сек (демо 14400) | **int8, часы** |
      | `67f82d94…` buzzer volume | uint8 | **int16** |
      | `84ccd3d4…` uart protocol | uint8 | **int16** |
      | `7e035080…` vario averaging | uint8, exp −1 | **int16, exp −3** |
      На подключённом приборе побеждает реальный CPF, поэтому баг не виден,
      но офлайн-режим и пресеты по ссылке кодируют значения не тем типом.

## Уже закрыто (2026-08-04, тот же заход)

Функциональная часть обращения Lennart — настройки не доезжали до прибора:

- Все GATT-операции сериализованы общей очередью (`src/utils/gattQueue.ts`) +
  ретраи транзиентных отказов. Причина: connect запускал ~80 параллельных GATT
  запросов, Android этого не выдерживает (BlueZ на десктопе прячет проблему).
- Запись характеристики больше не может «тихо не произойти»: нет CPF → берётся
  статический фоллбэк; нечитаемая/незаписываемая характеристика → исключение;
  после записи выполняется read-back и сверка.
- «Применено» отмечается только для полей, подтверждённых чтением с прибора
  (`markSyncedKeys`), неудачи показываются пользователем текстом.
- `diff()` больше не считает изменением то, что не удалось прочитать с прибора,
  и игнорирует не-настроечные ключи (симулятор больше не пишется в `local`).
- Округление вместо усечения при кодировании (1.15 м/с уходило как 1.14).
